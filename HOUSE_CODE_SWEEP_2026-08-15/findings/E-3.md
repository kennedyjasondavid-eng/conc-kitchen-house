### E-3-1 · Two independent hardcoded-version literals corrupt every persisted snapshot/export's provenance stamp
- class: kludge
- severity: P1
- status: NEW
- confidence: verified (traced both write sites at HEAD; confirmed the defect on the actual committed artifact, not just source)
- where: `index.html:31226` (`saveCanonicalSnapshot`, the canonical Save/snapshot-push path) and `index.html:26746` (`_buildUserDataExport`, the Settings→Data→Export path)
- what: `saveCanonicalSnapshot()` hardcodes `version: 'v9.8'` instead of reading the live `APP_VERSION` const (currently `'v9.49.36'`, defined at `:2068` and used correctly elsewhere — e.g. the version badge, `_diffSummaryForCommit`). `_buildUserDataExport()` independently hardcodes a *different* stale literal, `version: 'v9.49.12'` (current ~24 releases ago, per the CLAUDE.md changelog trail). Two separate single-source-of-truth violations of the same class, at two separate write sites, both silently drifting further from the truth on every release since whichever version they were last hand-edited to match.
- evidence: `snapshots/latest.json` (the most recent real snapshot, timestamped `2026-08-10T21:37:33.660Z`, i.e. produced by an app build well past v9.49.30+) carries `"version": "v9.8"` — confirmed by direct read of the committed artifact, not inferred from source. Source: `const snapshot = { timestamp: new Date().toISOString(), version: 'v9.8', state: gatherFullState(), sig, };` (`:31224-31229`). Import-side consumer at `:26880` displays this value verbatim to the user: `` `✅ Imported ${imported} items from ${data.version} (${data.exportDate}) · board refreshed locally` ``.
- consequence: Every one of the 44 committed `snapshots/*.json` files plus `latest.json` — the repo's own documented "audit log" (`snapshots/README.md`: *"Git history is the audit log; rely on it"*) — permanently misrepresents which app build produced it. Anyone (Jason, a future debugging session, an agent) trying to correlate a historical snapshot against "what did the app do at that point in time" via the `version` field gets a false answer frozen at v9.8, useless for the entire life of the repository from that point forward. The user-data export/import path has the same defect one version-generation fresher, surfaced directly in a user-facing toast on every import. Neither is a schedule-correctness bug (the fields are not consumed for branching logic — `importUserData` only checks *presence*, not value — so this is a trust/provenance defect, not a P0 data-corruption one), but it directly contradicts the app's own stated design principle of using dated artifacts as a reliable history.
- direction: Both sites already have the correct fact one line away — replace the literal with `APP_VERSION` (the existing global const used correctly by the badge and other export paths). This is the smallest possible fix (one seam, already in use elsewhere in the same file) — no new mechanism needed.

### E-3-6 · "Day Sheet" view shows dates from a stale, uncoordinated cycle anchor — same bug class the app already fixed once elsewhere, missed here
- class: kludge
- severity: P1
- status: NEW
- confidence: verified (traced both write sites, confirmed the correct canonical anchor exists and is used correctly elsewhere, confirmed the stale anchor's only two occurrences repo-wide, confirmed the consuming view is a live user-facing toggle, not dead code)
- where: `index.html:33631` (`dayDateLabel`, nested inside `renderDaySheet`) and `index.html:33691` (`getWeekDateRange`) — both consumed by the "Day Sheet" board view (`toggleViewLayer('daysheet', this)`, top-controls button at `:1708`, `data-tip="Daily work sections by site · view"`)
- what: The app has ONE canonical, correct rotation anchor — `HUB_CYCLE_START = new Date(2026, 5, 7)` (June 7, 2026, `:21756`) — consumed correctly by `getActiveCycleWeek()` and `serviceDateForSlot()` (both do proper `daysSinceAnchor % 28` modular wraparound against *today*, per their own comments: `serviceDateForSlot`'s comment explicitly says it exists because *"the conferral flagged 3 divergent cycle anchors"* and names itself *"the ONE canonical slot→date deriver"*). But `dayDateLabel()` and `getWeekDateRange()` independently hardcode a DIFFERENT, uncoordinated anchor — `new Date('2026-05-10')` (May 10, 2026) — and compute the displayed calendar date as `anchor + (currentWeek-1)*7 + dayIdx` with **no modular wraparound at all** against how many 28-day cycles have actually elapsed since that anchor.
- evidence: `:33631` `const anchor = new Date('2026-05-10'); // Wk1 Sunday (re-anchored 2026-05-19)` and `:33691` (identical comment/pattern). Compare `getActiveCycleWeek()` (`:21835-21846`), which normalizes to local midnight and does `((daysSinceAnchor % 28) + 28) % 28` — the correct pattern this repo already knows to use. The July 3, 2026 UX-audit "H1" changelog entry (CLAUDE.md) explicitly documents fixing *"the resource graph range off the stale May 10 anchor"* — confirming this exact anchor was already flagged stale once, and that fix evidently didn't sweep `renderDaySheet`'s two occurrences (repo-wide grep for the literal `2026-05-10` today returns exactly these two lines, nothing else — the resource-graph site is gone, these two are not).
- consequence: `currentWeek` (1-4) is correctly derived at boot via `getActiveCycleWeek()` against the true June 7 anchor and today's date. But when a supervisor clicks the "Day Sheet" view, `dayDateLabel`/`getWeekDateRange` re-derive the *displayed calendar date* from the stale May-10 anchor with no cycle-count correction — so instead of showing today's real date, they show a date from the FIRST 28-day cycle after May 10 (e.g. computing "Wk3 Tuesday" as ~May 26, 2026, regardless of whether it's actually August). This error grows by a full month every 28-day cycle that passes (currently ~3 cycles / ~3 months of drift as of this sweep) and will keep growing indefinitely — it is not a one-time bug that resolves itself. Secondary compounding issue: `new Date('2026-05-10')` (a bare ISO date string) parses as **UTC midnight** in JS, not local midnight, unlike the correct `HUB_CYCLE_START = new Date(2026, 5, 7)` — so even setting the date right wouldn't fully align with the app's own documented local-midnight-safe convention (`getActiveCycleWeek`'s own comment: *"Normalize both ends to local midnight so the time-of-day can't skew the floor"*). A supervisor cross-referencing the Day Sheet's printed/displayed date against a wall calendar or a DOOR plating sheet would see a date that's off by roughly a season — exactly the class of confusion the HUB sibling repo already had a real production incident over (the `_cycleStart` hot-fix documented in `conc-kitchen-hub/CLAUDE.md`).
- direction: Replace both hardcoded anchors with the existing canonical seam — call `getWeekDateRange`/`dayDateLabel` off `HUB_CYCLE_START` + the same modular `daysSinceAnchor % 28` pattern `getActiveCycleWeek()`/`serviceDateForSlot()` already implement, or better, derive the displayed dates directly via `serviceDateForSlot(week, day)` (already named in-repo as "the ONE canonical slot→date deriver") rather than hand-rolling a third anchor computation.
