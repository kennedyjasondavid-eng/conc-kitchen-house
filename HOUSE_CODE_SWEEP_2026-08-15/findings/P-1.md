### P-1-9 · DOOR `findOrphanSwaps` day-count uses raw ms division — a narrow, once-a-year DST-fallback boundary case can misjudge a swap pairing
- class: kludge
- severity: P3
- status: NEW
- confidence: verified (the arithmetic; the real-world trigger window is narrow and I did not simulate an actual DST-week run of the app)
- where: `conc-kitchen-door/index.html:15118-15142` (`findOrphanSwaps`).
- what: This diagnostic (not a live scheduling/routing path — it flags a "lone" meal-displacement swap for human review when it can't find a same-period partner within one 28-day rotation) computes `diffDays = Math.abs((new Date(date2+'T12:00:00') - new Date(date+'T12:00:00')) / 86400000)` then tests `diffDays <= 28`. Both operands ARE noon-anchored (good — protects against the calendar-DATE shifting), but the *subtraction* is still raw millisecond arithmetic divided by a fixed-size day (86,400,000 ms) — which is only exactly one calendar day when there's no DST transition between the two dates. Toronto's DST fall-back (gain 1 hour, first Sunday of November) makes a spanning pair compute `diffDays = N + 0.0417` instead of exactly `N`; spring-forward computes `N - 0.0417`. Because the check is a **fuzzy `<=28` threshold**, this only flips behavior in the narrow case where the true day-count is exactly 28 AND a fall-back transition falls inside that window — worked example: two same-period entries truly 28 days apart, straddling the Nov DST fall-back, compute `diffDays ≈ 28.042`, which fails `<=28` and the pair is (wrongly) NOT recognized as partners.
- evidence: `(new Date(date2 + 'T12:00:00') - new Date(date + 'T12:00:00')) / 86400000` (:15138-15140), no `Math.round`. Verified by hand-computing the ms delta a fall-back transition introduces (UTC-offset changes from -4 to -5, i.e. +3,600,000 ms local-noon-to-local-noon across the boundary) against the fixed 86,400,000 divisor.
- consequence: Low — narrow trigger (once/year DST week, exact-28-day boundary, same period, different date) and self-limiting (this only feeds a human-review flag, "orphan swap needing attention," not an automatic routing/allergen decision — worst case a legitimately-paired swap gets an unnecessary review flag, a false positive a human clears, not a missed real defect).
- direction: One-line fix reusing the file's own idiom: `Math.round(...)` the division (matches HUB's own `_wholeDaysBetween`, which does exactly this: `Math.round((b.getTime()-a.getTime())/86400000)` — an existing in-house pattern one file-name away in the sibling repo, not a new mechanism).
