### X-C-1 · `concRecipeSettings` — MISE's save is a stale-memory full clobber, not a read-modify-write
- class: footgun
- severity: P2
- status: NEW
- confidence: verified
- where: `conc-recipe-hub/index.html:23196-23201` (MISE `saveSettings()`), `:20725-20736` (MISE boot-time load, deep-merges `microsoft365` correctly at THAT moment), vs `conc-kitchen-hub/CONC_Production_Hub.html:3861-3870` (HUB `saveHubSettings()`, correct RMW)
- what: HUB's writer is a proper read-modify-write (`loadSharedSettings()` → mutate only `.microsoft365` → `setItem`), safe by construction. MISE's writer is NOT: `saveSettings()` does `localStorage.setItem('concRecipeSettings', JSON.stringify(snapshot))` where `snapshot` is `JSON.parse(JSON.stringify(currentSettings))` — a serialization of MISE's **in-memory** settings object captured at MISE's own page load, never re-read from storage before the write.
- evidence: `const snapshot = JSON.parse(JSON.stringify(currentSettings)); ... localStorage.setItem('concRecipeSettings', JSON.stringify(snapshot));` (MISE :23196-23201) — no `getItem` in between. HUB's writer, by contrast: `const existing=loadSharedSettings(); existing.microsoft365=s; localStorage.setItem('concRecipeSettings',JSON.stringify(existing));` (HUB :3866-3869).
- consequence: two HOUSE apps sharing one origin, no `storage` event listener anywhere (grep-confirmed 0 hits app-wide) and no live coordination. If a staff member configures the SharePoint `microsoft365` block via HUB Settings in one tab, then later saves ANY unrelated MISE setting (order pantry text, AI toggle, mirepoix bundle) in a MISE tab that was opened/loaded before that HUB edit, MISE's save silently reverts `concRecipeSettings.microsoft365` to whatever MISE had in memory at its own boot — erasing HUB's edit with no error, warning, or diff shown to either user. Scoped to the SharePoint-sync config block only (not menu/allergen/food-safety data), and that integration is still pre-rollout per `HOUSE_SHAREPOINT_IT_BRIEF_2026-07-07.md` (Stage-1/2 ask still pending IT) — so today's blast radius is low, but the pattern will bite harder once SharePoint sync goes live and both apps' Settings panels are routinely used.
- direction: MISE already has the correct pattern one function away — mirror HUB's `loadSharedSettings()`-then-merge shape: re-read+merge `microsoft365` (and any other cross-app-owned subtree) from the live key immediately before `setItem`, the same way MISE's own boot-time loader already deep-merges each subtree instead of trusting a single shallow spread.

### X-C-2 · `conc_gh_token` — shared credential, divergent sanitization (EXPO scrubs on read, HUB does not)
- class: footgun
- severity: P2
- status: NEW
- confidence: verified
- where: `conc-kitchen-expo/index.html:22341-22352` (`getGHToken()`, strips `[^\x20-\x7E]` + trims on every read) vs `conc-kitchen-hub/CONC_Production_Hub.html:1078-1081` (`getHubToken()`, raw `getItem` only) and its sole network use at `:4740` (`saveOverrides()`, `'Authorization': 'Bearer ' + token`)
- what: `conc_gh_token` is written by both EXPO's Settings (`saveGHToken`, only `.trim()`) and HUB's Settings (`saveHubConnect`, only `.trim()`) with no non-ASCII stripping at write time on either side. EXPO added a **read-time** sanitizer specifically because "Non-ISO-8859-1 characters (smart quotes from rich-text paste, invisible whitespace, etc.) in the token break the fetch Authorization header with the error: 'String contains non ISO-8859-1 code point'" (EXPO's own v9.29 changelog, CLAUDE.md). HUB's `getHubToken()` has no equivalent guard and feeds the raw value straight into a `fetch` Authorization header for the day-notes GitHub push.
- evidence: EXPO: `return raw.replace(/[^\x20-\x7E]/g, '').trim();` — HUB: `return localStorage.getItem('conc_gh_token') || localStorage.getItem('hub_gh_token') || '';` then `const ghHeaders = { 'Authorization': 'Bearer ' + token, ... }` with no scrub in between.
- consequence: because the key is explicitly shared "by all HOUSE apps on this device" (EXPO's own storage-key label, `:31365`), a token pasted with rich-text artifacts (copied from Outlook/Word/Slack — the exact scenario EXPO's fix documents as having actually happened) will silently work fine everywhere EXPO reads it (scrubbed on every read) but can throw HUB's day-notes save with the identical low-level fetch error EXPO already fixed for itself — a "works in one HOUSE app, breaks in another" symptom for what looks like one shared credential, with no diagnostic pointing at the real cause.
- direction: HUB has the fix already written next door — port EXPO's one-line sanitizer into `getHubToken()` (or better, sanitize once at the shared write sites in both apps' Settings-save handlers, closing the root cause instead of patching every reader).
