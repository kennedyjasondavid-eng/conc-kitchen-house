## Telos — what we're actually building

HOUSE exists so CONC can feed ~185–200 shelter residents (three dietary streams, multi-site, a 4-week rotation) **reliably and with dignity**, built in-house at **zero external cost** on infrastructure the non-profit already owns. The point was never "software" — it's that the money goes to *food and people, not vendors*, and that the operation **cannot quietly fail**.

Two things crystallized this session:

1. **Polish is function here, not vanity.** These tools are used by real staff *every shift* — fast, under load, in a domain where mistakes have weight (anaphylactic allergens, halal/vegan compliance, people who don't eat if the board is wrong). A calm, legible, trustworthy interface lowers cognitive load and error rate. Craft also signals care — for the staff using it, and through them, the residents. A board that looks respected gets trusted and used.
2. **Coherence *is* the product.** "Enter the data once; generate everything downstream" means files can't disagree — there is one source of truth. In a high-stakes operation, that coherence is trust. The UI's whole job is to make that single source legible at a glance.

> **The telos:** operational excellence in service of dignity — cheap enough to be sustainable for a non-profit, and crafted well enough that the people doing hard work feel *equipped, not burdened.*

## Insights — why the redesign worked

- **Subtraction beats addition.** The biggest wins were *removals*: the muddled "View" row, the inconsistent glyph soup, three stacked toolbars → one bar. Clarity came from taking away and then committing to what's left.
- **One confident accent system carries meaning.** Forest green = *"where you are"* (banner, active week). Mint = *"act now"* (Today, the pinned primary, pins, the wordmark dot). Exactly **one saturated accent at rest** — the eye always knows where to go.
- **Identity flips a tool from "interface" to "product."** The smallest change with the biggest perceptual payoff was the **"HUB." wordmark** (heavy, open tracking, mint period). It says *this is a made thing, cared for* — which matters because it represents CONC's care.
- **Personalize where it pays; default to calm.** Pinnable downloads let each user shape their own quick-paths (the docs *they* print) without bloating the default for everyone.
- **Discoverable ≠ always-visible.** Collapsed-by-default + a *prominent* marker + a *faded* "more docs" cue is cleaner **and** still one tap. "Maximally functional" never meant "everything on screen."

## The HOUSE design language (port this to CODEX / DOOR / EXPO)

The shared palette already exists (`--hd` forest, `--ac` mint, `--sf`/`--bl`/`--bd`/`--tx`/`--tm`, dark via `[data-theme]`). The vocabulary the HUB now demonstrates:

- **Chrome** — one **sticky control bar** over stacked toolbars; a **single merged status line**; round **icon buttons** for low-frequency utilities (dark mode, settings, reload); a slim forest banner carrying a **bold, tracked wordmark + mint period**.
- **Controls** — **segmented pill groups** (active = forest fill, inactive = mint outline); **ghost pills** for secondary actions; exactly one **mint-filled primary** CTA; small site/filter pills.
- **Disclosure** — **collapsible trays** (`<details>`, zero/low JS, works `file://`) with a prominent marker + faded hint; **user-pinnable favourites** persisted to `localStorage`, surfaced in the collapsed state.
- **Type** — DM Sans (UI), DM Mono (numbers); the wordmark *is* the identity.
- **Non-negotiables** — one accent at rest; responsive rules scoped `@media screen` so **print never breaks**; no-FOUC gating; **everything themes via vars** (no hard-coded colors); ≥40px touch targets.

## Process wisdom (how to work in this ecosystem)

- **Iterate in the user's real view.** Jason watches the *served file* live in the Launch preview panel — so edit the real file directly; separate mock-up files don't show there. Mock-ups only help when you can screenshot them — and the HUB page can't be captured in automation (it never reaches `document_idle`); verify via DOM/`eval`. (See the `project-hub-status` memory.)
- **Confer with subagents on genuine forks.** The layout choices and the downloads tray got better after an adversarial agent review — but have them check the *real* file's constraints (vars, print, gating); they sometimes mis-detect the repo.
- **The user is the visual judge.** Tight loop: propose → apply live → react → refine. Offer real choices at real forks; recommend, don't enumerate.
- **Single-file HTML is a strength.** No build step → the served artifact *is* the source → fast iteration, zero drift.

## Four-cause reflection — sharpening the telos (2026-06-08)

*Written mid-CODEX-cook-surface, after applying Aristotle's four causes to the work and conferring with an adversarial agent. A reflection earns its keep only by surfacing where the maker was wrong — these are the load-bearing corrections, the ones that cost something. (The harmonious observations didn't survive the review.)*

**1. The telos is invisibility, not excellence.** VISION.md states it truer than the telos at the top of this doc: *"the system becomes invisible to the operation… nobody mentions EXPO at standup. That's complete."* "Operational excellence, crafted well" is pitched at the **artifact** — the tool being good. The real telos is pitched at the **operation** — the tool *disappearing into the work it serves*. A tool whose telos is to be admired has mistaken itself for an end. So polish, identity, and craft are **instrumental**: good insofar as they make a tool trustworthy enough to recede, suspect the moment they recruit attention to the artifact. Craft should be **felt, not seen** — a good knife disappears into the hand; a bad one announces itself. By this test the **"HUB." wordmark is on probation** — it is *seen*; justified only up to the trust threshold, vicious past it. When in doubt, recede.

**2. Separate the irreversible from the reversible, and govern them differently.** The recurring design move across HOUSE: **route the on-the-line / irreversible case under caution; let the off-line / reversible case run free.** The deployed tool must not quietly fail — a branch may fail loudly. The anaphylaxis signal gets caution; mock data runs free. The single source gets verification; a throwaway draft doesn't. One principle unifies the branch decision, the agent-gates, the graded allergen caution, and the cook-first default. **Match the ceremony to the stakes** — gate the telos-laden and irreversible; never burden the trivial and reversible.

**3. Coherence is the load, not the virtue.** "Enter once, generate everywhere" means one source of truth — and therefore **one source of *catastrophe*.** An error in the single source propagates to every app at once, with no disagreeing file left to act as a smoke alarm. Coherence doesn't lighten the correctness burden; it **transfers all of it upstream** to the source and the maker who authors it. So *the more coherent the system, the more verification must move to the source.* The allergen caution and the adversarial gates aren't niceties bolted on — they're the **compensating controls a coherent system structurally requires.**

**Three sharpenings of the practice (from the four causes):**
- **The form is a small fixed grammar; coherence is only its consequence.** The test for every addition is VISION's: *did this add vocabulary, or only data?* (Scale-to-N re-renders a quantity the recipe already holds → clean. A new stored field bought for one feature would be formal corruption.)
- **An agent is a second, fallible efficient cause — to be governed, not an instrument.** It contributes *form* (it caught a double-rounding bug; it can also import a wrong one). Brief it fully, ask a specific question, expect it to find what you missed — and **own the decision.** And name the privation honestly: the lone maker is the current efficient cause *and the bottleneck the vision is dissolving* (architect → dimension-keeper; "editable by anyone who knows the operation"), not a romance to preserve.
- **Work with the grain — including the grain you can't see.** *Technē* is making in accordance with the matter's real nature *under its appearance* ("read before cutting" is the epistemic precondition, not mere caution). In a cascade your matter is a downstream app's source, so reverence must extend to wiring invisible from where you stand — a CODEX element id may be DOOR's source.

## Working with agents on a multi-step build (2026-06-09 — the CODEX cook surface)

Two durable lessons from shipping a 9-step UI stage and conferring the roadmap with adversarial agents:

- **Before building a cross-app feature, find the seam that already exists.** The plan was to build CODEX "Service Mode" by having CODEX fetch DOOR's menu + counts. A confer against the *real code* found the integration already exists — CODEX parses `?recipe=`, and HUB already loads the counts, matches dish→recipe, and deep-links into CODEX. The feature collapsed to ~5 lines (`&portions=N`), not a new engine — and the "fetch DOOR" design would have closed a dependency cycle and duplicated HUB for zero gain. **In a one-way cascade the integration point is usually already there; reimplementing it both adds coherence load and breaks the cascade. Verify what exists across the apps before adding a dependency edge.**
- **The "verify-the-finding" half of an adversarial gate is the load-bearing half.** Gating each step with a reviewer — then having a *second* agent try to **refute** each finding — did what single-pass review can't: it killed false positives (two "coherence problems" were correctly judged intentional design and dropped) *and* confirmed real defects with rigor (a light-mode AA failure, a malformed tooltip from literal quotes in help strings, a printed card that went silent on allergens). **Find-then-refute earns trust in the GO and prevents both over- and under-reaction.** Scale the gate to the change: a single skeptic for a small step, a multi-lens find→verify workflow for a complex or safety-critical one.


## The provenance anti-pattern, caught in the wild (2026-06-09 — CODEX salt bug)

A live bug sharpened the rule the rest of this doc keeps circling. CODEX was injecting an *estimated* quantity — assumed salt (1% of total batch weight, water included) added so "salt to taste" recipes wouldn't report 0% sodium — as a **real stored ingredient**, and **mutating the recipe to do it** on every export, save, and import. A cook's printed card for Arroz con Pollo (no salt in its ingredient list; salt lives in the *method*) showed a phantom **Salt 1.6 lb** line. A cook following that card oversalts ~185 meals.

- **An estimate is not a datum. Compute it read-only; never write it back into the source.** Sodium needs a salt assumption — but the assumption belongs in the *nutrition calculation* (read-only, re-derived each time), not appended to the ingredient list. Same principle as display-only scale-to-N and VISION's "portions-tonight must never write the recipe": **derived / deployment values must not corrupt the portable source.** The test for any feature touching the source stays — *did this add data, or mutate the source to fake data?*
- **Coherence makes a quiet write catastrophic.** Because CODEX is the *single* upstream source, a mutation on an innocuous-looking path (an export button, an autosave) silently propagates to every downstream consumer with no disagreeing file to raise the alarm — exactly "coherence transfers all correctness upstream." The compensating control is to **forbid writes on read paths by rule**, not to trust that a given export "probably won't persist." The library-save path *did* persist it.
- **The lone maker is also the QA — so the real artifact is the test.** This wasn't found by reading code; it was found by the architect **opening the generated XLSX** and seeing salt the screen never showed. *Read (and run) the real downstream artifact before trusting the path that makes it.* The screen and the export disagreeing IS the smoke alarm a coherent system otherwise lacks.
- **The gate's refute-half earns its keep again.** The adversarial review confirmed nutrition was preserved (sodium still estimated read-only) AND surfaced the *same* anti-pattern hiding in a sibling path (the recipe importer), which was then fixed for consistency. Finding the fix is half; proving it complete (no second injector) is the other.


## Securing a coherent app — the XSS class, two review shapes, and the deployed-build oracle (2026-06-13 — CODEX)

Closing an app-wide stored-XSS class in CODEX (a cook-log review finding that turned out to be ~57 unescaped `innerHTML`/`document.write` sinks) produced four lessons that generalize to every HOUSE app:

- **In a sharing/import ecosystem, "trusted local data" expires — re-ask *who can author this string?***. CODEX had a documented "accepted norm": recipe names are typed by the local author, so leave them unescaped. That premise quietly died when **XLSX import** and **site-collection / nomination sharing** made recipes arrive *off-machine*. The same shift that makes the cascade powerful (data flows between apps) widens every app's threat surface. **When a value can cross a machine boundary — import, share, multi-user entry, a downstream fetch — it is untrusted at the render sink regardless of who "owns" the feature.** Retire any "it's our own data" exemption the moment a sharing or import path is added.
- **Escape at the sink, with the right escaper for the *context*.** Wrap the interpolated expression at the point of HTML assembly — never reassign the underlying variable (that would corrupt the stored/exported datum; same read-only discipline as the salt bug and scale-to-N). And the escaper must match the context: a text/`"`-attribute escaper (`& < > "`) is *not* enough inside an inline handler `onclick="fn('VALUE')"` — that single-quoted JS-string-in-a-double-quoted-attribute needs the `'` escaped too (a dedicated `_escJsAttr`). One escaper is not a security policy; context is.
- **Run two review *shapes* — by-region and by-dimension — because each is blind to what the other catches.** A 60-agent sweep that *tiled the file by line range* found most sinks but **under-covered template-literal-heavy helper functions** (`buildOrderListHTML`, `buildMacroPanelHTML`) — they fell between an agent's window and its attention. A second, independent **by-dimension completeness review** (one lens whose only job was "what untrusted text still reaches HTML?") found 7 more. Coverage-by-territory and coverage-by-property miss different things; for anything safety-critical, do both.
- **The deployed build is the oracle, and an empirical payload-scan beats a grep.** Static greps for `.name`/`.note` tokens missed a *derived* variable (`catBadge`) that still carried tainted text; **rendering a malicious payload and scanning the DOM for live `[onerror]` elements caught it.** This is the salt-bug lesson again — *run the real artifact* — applied to security: end an escaping pass by injecting a probe and querying `document.querySelectorAll('[onerror]')`, not by trusting the diff. (Verify via DOM/`eval`: this app's served file never reaches `document_idle`, so screenshots/playwright hang — eval and fetch-the-served-bytes do not.)


## EXPO Phase 3A — routing as data (2026-06-14)

*From EXPO's Phase-3A refactor (the override priority-chain → a profile-driven capability matcher) and the Phase-5 MISE-bridge fix. The sections above are mostly about interface; these are about the engine — but the same grammar drives both: push complexity out of code and into data the architect owns.*

> **EXPO's full routing/engine grammar** — 18 principles incl. provenance, the **recipe↔deployment cleave**, and **wizard-as-conversation** (the friction-free knowledge-extraction model for supervisor edits) — lives in `conc-kitchen-expo/EXPO_DESIGN_PRINCIPLES.md`, with the routing contract in `schemas/ROUTING_MODEL.md` and operational ground-truth in `CONC_OPERATIONS.md`. The four principles below are the cross-HOUSE-relevant distillation; read the EXPO docs before an EXPO engine/edit-surface pass.

- **Routing belongs in a capability profile, not in code.** When logic branches on the *identity* of a thing — site-name literals, an override table keyed by name — ask whether it should branch on a *capability the thing declares.* EXPO's `routeItem()` reading `site_profiles/conc_reno.json` replaced hundreds of `Bloor`/`Rex` literals and branching guards, so "where does this cook?" became a question answered by data the architect edits. The payoff isn't fewer lines — it's that a mode transition (reno→standard, add a site, change a capability) becomes a **profile edit, not a refactor.** Safe ordering for a swap this load-bearing: **shadow** (run the new path silently, prove 0/0/0 parity against the old) → **cutover** (matcher authoritative) → **delete** (remove the legacy layers once nothing reads them).

- **A variation field on the entity beats a parallel override table.** To say "X behaves differently in mode M," put a `renoVariant:{equipment,ovenMin,…}` block *on the base record* — not in a shadow table keyed by name. Three wins: it's co-located with what it varies (one place to read); it survives the upstream sync (the MISE bridge overwrites *sync fields* from CODEX, and a variant block isn't one); and when the mode ends the base record is already correct, so no teardown corrupts it. The shadow table is the cheapest *rollback* during a transition — but the durable home for the knowledge is the entity. (Data-as-product in miniature: encode the constraint as a field, not as logic smeared across a lookup layer.)

- **Before deleting a shadow/reference table, audit what knowledge it encodes.** `RENO_ITEM_OVERRIDES` looked like scaffolding but carried facts derivable nowhere else: *which* `cookSite:Rex` items flip in reno (CODEX library imports must NOT flip — `cookSite:Rex` alone is insufficient, so a blanket flip broke ~182 items), `chainType` lifecycle suppressions, and `rexInputs`/fillings that lived only there. A table that documents "which X belong to category Y" is deletable only after (1) the membership relocates onto the entities (here a `renoFlip:true` marker on the affected base recipes), (2) you enumerate every field its consumers read and confirm each survives in the base store or moves to the entity, and (3) a **stratum-invariant gate** fails loudly if any consumer still reads a now-missing field. Reference tables hold domain knowledge, not just redundancy — audit before you delete.

- **Stack determinism gates — schedule-shape, per-item, and live-soak each see what the others miss.** For a routing/data change, one gate isn't enough: a **schedule-shape** diff (items added/removed/changed) catches regressions that net to zero *items*; a **per-item census** (new-path vs old-path, every item) catches mis-routes that net to zero *shape* change; and a **live-tab soak against the real deployed state** catches what both offline gates are structurally blind to — the MISE bridge overwriting baked values from live CODEX. (That blind spot was not hypothetical: a live soak found CODEX silently zeroing on-menu cook times — Meatloaf/Vegan-Philly oven minutes → 0 — that the offline gate, running embedded data, could never see.) A change that passes only one layer is under-verified. The determinism-domain sibling of the find-then-refute and run-the-real-artifact gates above: measure the shape, the items, *and* the live state.
- **The "variation field beats an override table" scar also hides in hand-written generators — and its tell is a no-op edit.** (2026-07-01, EXPO S5.) A generator that hard-codes a routing field (`addStandardBloorColdPrep` writing `site: SITES.BLOOR`) usurps the entity's declared field exactly as an override table does, one layer downstream. The tell: flip the entity field (`cookSite`) and the output doesn't move — a *schedule-neutral* edit is ambiguous between a **dead scar** (nobody reads the field → delete it) and a **usurped field** (a producer overwrites it → re-enfranchise it by branching the producer on the field). Same green signal, opposite fixes; disambiguate by who-reads / who-overwrites in the *source* before deleting (the artifact oracle can't tell them apart — both values are ignored). And landing that fix reds the gates that encoded the old hard-coded behavior: re-pin them to the new truth, don't loosen them. Full grammar: `conc-kitchen-expo/EXPO_DESIGN_PRINCIPLES.md` #54 (gate rule #53, merge-verify corollary #51). *Point, don't restate.*


## HUB Step 5 — a feature can be silently dead while its code is intact (2026-06-14)

*From HUB governance Step 5: verifying the boot-time `hub_schedule_version.json` check. The version-decision logic was already correct — the discovery was elsewhere, and it generalizes to every single-file HOUSE app.*

- **JS readers can outlive the DOM element they target — and grep says everything's fine.** HUB's stale/error/provenance banner wrote into `#builtTs` from four code sites, but that element had been dropped in a header redesign while the readers were left behind. `getElementById('builtTs')` returned `null`, `_setBanner` hit its `if(!tsEl)return` no-op, and the **whole visible-degradation feature was dead** — no crash, no log. A grep for `builtTs` *looks healthy* (the token is all over the code); only a **runtime DOM check** (`!!document.getElementById('builtTs')`) reveals the broken binding. Where markup and handlers drift independently, verify the *binding at runtime*, not the *reference in source* — the "run the real artifact" rule applied to DOM wiring. Fix the root cause (restore the element), don't paper over the readers.
- **A null-guard that prevents a crash also hides the failure — degrade *visibly*, not just safely.** `if(!tsEl)return` correctly avoided a `TypeError` (never hard-fail ✓) but turned a missing-element bug *silent* — the worst outcome for a board whose job is to warn staff that data is stale. Match the response to the stakes: a missing decorative sink can stay quiet; a missing **safety-signal** sink should leave a trace. "Safe" must not become "invisible."
- **A scoped adversarial review earns its keep on the thing you didn't ask it to check.** The task was "tighten the version-check warns"; five lenses confirmed the decision logic was already correct, but the by-degradation lens surfaced the dead banner as a **blocker bigger than the assigned task.** Pointed at a narrow task and briefed on the *contract* (not just the diff), find-then-verify widens the frame and catches the adjacent, higher-severity bug.


## Hardening a single source + operating multiple sessions (2026-06-18 — DOOR)

*From hardening DOOR's publish path end-to-end (PRs #48-#52), an independent recall-mode review, and untangling a parallel-session clobber. Three carry-forward lessons.*

- **At the single source, *refusing* to publish a malformed output beats publishing it with a warning.** DOOR is upstream of everything; a structurally-broken `menu_current`/`routing_by_meal` doesn't just look wrong, it propagates to EXPO + HUB with no disagreeing file to raise the alarm. So when the preflight finds a *deterministic* structural defect (a missing required day, a fractional count), DOOR now **blocks the publish** instead of shipping it red — and downstream degrades to its **last-good-valid cache** (stale but correct) rather than ingest corruption. This is "coherence transfers correctness upstream" grown teeth. Two guardrails keep it from being reckless: block only on *no-false-positive* structural violations (keep judgment-laden / clinical flags advisory), and **prove the validator passes the real checked-in artifacts before it gates the feed** — a blocking validator becomes load-bearing, so demonstrate its correctness on live data and leave an operator override as the escape hatch.

- **A test can prove the producer while missing what staff see — drive the result through the wrapper.** A "publish goes red on bad data" fix was correct *inside the function under test*, but a wrapper (`publishAndSync`) overwrote it green on the default auto path — and the unit test only called the inner function directly, so it stayed green while the visible bar lied. Find-then-refute caught it; the test couldn't. When a fix's effect is rendered by a *caller* the test never exercises, the test verifies the mechanism, not the user-visible outcome — add a test that drives the value through the wrapper. (A recall-mode review on the same change also surfaced an auth footgun the suite missed — an unsaved token left in the Settings field silently blocked *background* publishing — reinforcing that the harness can be blind to the path that actually fires.)

- **The working tree is a shared mutable resource — one writer at a time, or you clobber.** Two AI sessions editing the same OneDrive repo folder concurrently silently swept one's edits into the other's commit. Recovery: classify hunks by a unique symbol they each touch, split losslessly (`main` + both halves must reconstruct the original byte-for-byte), test each branch alone. Different repos are safe; the hazard is two writers in one working tree — give each concurrent session its own **git worktree** (outside the OneDrive-synced folder) on its own branch. And **verify a parallel session's *report* against the actual tree, not its word**: a handoff that claimed "patch applied, 55/55 passing" had in fact been clobbered into a different commit. The report is a point-in-time claim; the working tree is ground truth — the deployed-build-is-the-oracle rule applied to cross-session handoffs.


## The germ recurs — and is a design test (2026-06-20 — EXPO)

*From EXPO's editing-experience work: Jason recognized that deriving a Decision's "breadth" from the shape of what it targets was "an echo of the EXPO germ mantra." It is — and naming why generalizes across HOUSE. He called it bedrock. (EXPO's full framing: `conc-kitchen-expo/EXPO_KERNEL_VISION.md` "The mantra recurs" + `EXPO_DESIGN_PRINCIPLES.md` #41.)*

- **Each app's founding sentence is fractal — it should hold at every scale, and the rhyme is how you know a small decision is right.** EXPO's germ is *"the menu items tell you what jobs they need."* It recurs: macro (menu → jobs), middle (a supervisor's reasoned fact → the schedule, via the Decision Ledger), micro (a Decision's target → its breadth — already implied by the target's shape, so *derived, not stored*). When the clean answer to a sub-problem turns out to be a re-instance of the germ, you're cutting *with* the grain; when it forces a new stored field or a special case, suspect you're cutting against it. This is the same shape as HOUSE's own germ — *"enter the data once; generate everything downstream."* The recurrence is *convergence of form across scales* — the sibling of the existing "convergence is the evidence an abstraction is right."

- **The mantra, turned to face the schema instead of the schedule, is a working test: *can this be read off what's already declared?*** If yes, **derive** it (a thin reader, never a stored field). If no — if it's genuinely irreducible — **store** it, and only then. This is the rule the scattered HOUSE precedents above are all instances of: *an estimate is not a datum* (the CODEX salt bug — compute read-only, never write back), *routing belongs in a capability profile, not code*, *a variation field on the entity beats a parallel override table*, *portions-tonight must never write the recipe*. All of them are "don't store what the source already implies." (Worked example: a Ledger edit's *breadth* and *temporal* and *site* axes sort under the test — temporal and site are irreducible → stored; breadth is implied by the target → derived. Two stored axes, one reading.)

- **A stored copy of a derivable fact is a second truth that can disagree with the first — the exact drift a single source exists to prevent.** So the test isn't tidiness; it's the structural guard. The cost of getting it wrong is the footgun one level up: two records that fall out of sync, with no disagreeing file to raise the alarm — the direct corollary of "coherence transfers all correctness upstream." Derive-don't-duplicate is how a coherent system keeps the single source single.


## Gating a feature that handles user-authored state — the baseline blind spot (2026-06-20 — EXPO "My Changes")

*From building EXPO's read-only "My Changes" trust surface (a view over the user's edit-ledger) and its three multi-agent reviews. Every real defect — two stored-XSS holes, a stale-fridge phantom, a sleeping rule shown as broken, a silent wrong-shape decode — hid in the same place: **the gap between the inert baseline the gates trust and the populated, adversarial state the feature actually runs in.** One sentence to carry: the green baseline can be green precisely because the feature does nothing yet.*

- **Gate the state the feature exists to operate on — including its hostile form — not the clean baseline.** A feature whose job is to handle user-authored data is *inert* on an empty store, so a schedule-neutrality gate (here `ux_diff` 0/0/0) passes **because it isn't exercising the feature at all** — "green-but-hollow." Real coverage means seeding the store with authored Decisions *and* their adversarial versions (a hostile id, a hostile field-name, a row that moved, a rule that's asleep), then asserting on *that*. Both XSS holes, the fridge bug, and the dormant-shown-as-red were all populated-state-only; none could appear on the baseline the gates ran. The blind spot is structural: when a gate is green *because* the change is inert at rest, it is testing nothing about the change.

- **A read-only / view / preview / export surface needs a *purity* gate, distinct from any output-diff gate.** An output diff (schedule diff, render diff) is structurally blind to a *silent write* that produces no output change — the exact failure mode of a "read-only" view that quietly memoizes into the store or stamps a derived field. The catch is cheap and reusable: snapshot the source (the store + localStorage + a row/record count) before and after the read op, assert **byte-identical**, plus a **rebuild/recompute call-counter of 0**. "Read-only" is a claim; this is the assertion that makes it falsifiable.

- **When you fix a class of bug in a function, sweep its siblings — and re-audit every render sink the moment a store gains an import/share door.** The coherence-review XSS was a *pre-existing* unescaped board-marker two lines above a *new, correctly-escaped* one: escaping the new sink is the cue that its neighbors need the same. And it was reachable only because the edit-ledger had gained an **import path** — which silently turned "our own ids / our own key names" into off-machine, untrusted text at the sink. This is the CODEX stored-XSS lesson (escape at the sink, right escaper for the context; "trusted local data" expires when a sharing/import path is added) confirmed in a second app: **adding an import door to any store re-opens the threat surface of every sink that store feeds — re-audit them.**


## The interface shows known-state in the user's language — most UI bugs are a known≠shown divergence (2026-06-21 — cross-HOUSE)

*From EXPO's v9.37 UX sweep. It arrived as two unrelated-seeming complaints — "the trust surface lies" and "the edit panel is cluttered" — that turned out to be one duty failing in two directions. The engineering-grammar form lives in `conc-kitchen-expo/EXPO_DESIGN_PRINCIPLES.md` #46–#48; the lodestar form in that repo's `EXPO_KERNEL_VISION.md` ("the interface is the other half of the kernel — known-state, shown faithfully"). This is the cross-HOUSE distillation — point at the EXPO docs before an EXPO edit-surface pass; don't restate them.*

- **Every HOUSE app is an engine that *knows* and a surface that *shows* — and the surface has nothing of its own to say.** DOOR knows a resident's routing and allergens; EXPO knows a dish cooks eight days ahead; HUB knows what's due; MISE knows an allergen. The surface's only job is to reflect what the engine already knows back to the human — faithfully, and in the human's language. When it's doing that job it's a clear window onto the truth — which is exactly what "the system recedes into the work" means (the telos at the top of this doc). This is the kernel seen from the other side: the schedule/output is the *fixpoint of every asserted truth, reconciled*; the interface is that fixpoint *shown*. Engine half and interface half are the same idea from two sides.

- **So in a coherent, single-source system most interface defects are NOT missing features — they are a gap between known-state and shown-state.** The engine knew the truth and the surface presented something else. Two failure modes: **unfaithful** — the shown thing is *false* relative to known-state (EXPO's audit that *knew* an edit applied but *showed* "nothing matched"); and **illegible** — the shown thing is *true but in the engine's jargon* (a panel that *knew* the cold-chain consequence but *showed* an oven-minute spinner). Same duty, same cause: the surface was *plumbing the engine's internal representation to the screen* instead of *deriving a human view from known-state*.

- **The cure is the founding principle, one layer up: derive what is shown from what is known, fabricate nothing, and say it in the domain's nouns.** A zero-fill or a false status is the patched-output lie in the display layer — a value that was never asserted, presented as if it were (the salt-bug / derive-don't-duplicate rule pointed at the screen). And "faithfully" carries a second clause — *in the user's language*: domain nouns ("cooked ahead · cold round-trip"), not field names ("oven-min"). A surface that adds a truth of its own (a fabricated zero, a false "nothing matched", a raw id) has stopped being a window.

- **The transferable diagnostic — carry this into every app:** when a screen feels wrong, do **not** ask "what feature is missing?" Ask **"what does the system already know that this view is hiding, distorting, or showing in its own jargon instead of the user's?"** That question finds the bug *and* predicts the next one — it's wherever a surface shows internals instead of a translation of the truth. **DOOR is the highest-stakes place to ask it:** a routing / compliance / allergen indicator that diverges from a resident's actual record is the *unfaithful* failure with food-safety consequences — the display-layer sibling of the upstream "refuse to publish a malformed output" rule (2026-06-18, DOOR).

- **Validated across HOUSE the day it was written (2026-06-21).** A by-app diagnostic sweep asking exactly that question surfaced the *same shape* — a display/export surface reaching past the engine to a raw, frozen, or zero-filled value instead of re-deriving the truth the engine already owns — independently in three apps built at different times: **DOOR** (the red anaphylactic banner re-scrapes raw resident tags instead of reusing the conflict enforcer's predicate, and can even render an empty `()` when the sole trigger is `GF`), **HUB** (schedule freshness is version-*equality*, so a stale-but-served board reads "current"), and **MISE** (the allergen feed writes `entry.allergens || []`, flattening *never-verified* into *analyzed-clean*). Three independent instances of one shape is the convergence-of-scars evidence that the lens is real, not a frame imposed after the fact (the test EXPO names in `EXPO_DESIGN_PRINCIPLES.md` #25). The per-app punch-lists live in each repo's `KNOWN_VS_SHOWN_FINDINGS.md`; they convert into owner-lessons as each fix ships.


## "Inert now" is not "safe" — review a diff against the roadmap, not just its current readers (2026-07-10 — EXPO "My Changes" Stage 1)

*From the Changes-acceptance UX build (EXPO PR #165). The engineering-grammar form of the gate-discipline half lives in `conc-kitchen-expo/EXPO_DESIGN_PRINCIPLES.md` #55–#56; this is the cross-HOUSE distillation — point at those before an EXPO gate pass, don't restate them.*

- **A change to a shared structure can be perfectly correct against every *current* reader and still be a landmine for a *planned* one — and "schedule-neutral / all-gates-green" cannot see it.** The whole-PR architect review caught a stale/circular value in a decision field (`supersededBy`) with **zero current readers**: every gate was green, behavior was correct, snapshot round-trips were fine — *because nothing read the corrupted part yet*. But the next planned slice derives archive membership from exactly that field. The fix was one line, folded now; the point is that a diff-scoped or gates-only review would have waved it through. **When a change mutates a structure future work will consume, review it against the roadmap, not only against today's call sites** — the integrity of the data matters before anyone reads it. (This is the *temporal* sibling of the baseline blind spot above: there the gate was green because the feature was inert *at rest*; here the bug was invisible because its consequence stays inert *until a later slice ships*.)

- **The enforcement blind spot — a corollary of "a feature can be silently dead while its code is intact" (HUB Step 5), one layer down.** A *gate* that exists, passes locally, and is not in the CI runner's list enforces nothing while reading as coverage in the tree — false confidence that review found only by asking "does every gate this slice leans on actually *run* in the required job?" (EXPO's `baseline_accept_gate` had been green-locally-only, unenforced, for weeks.) Same shape as a dead feature with live-looking code: check reachability of the *enforcement*, not just presence of the test file.

- **Two process notes that earned their keep this build.** (1) *Mutation testing beats "the test passes" for proving a gate is adequate* — an independent reviewer who breaks the code and confirms the gate reddens catches a gate that's testing nothing (e.g. a human-readable source-scan matching a *comment*) in a way a passing run never will; reach for it on anything safety-adjacent. (2) *Scale review intensity to stakes* — a single skeptic for chrome/display, two lenses for anything touching data semantics, and a roadmap-aware architect pass for the whole PR each caught a *different* bug class at a different depth (a focus regression, a CI-enforcement gap, a latent future-landmine). One review shape would have missed two of the three.


## The only boot that matters is the returning-user boot — test from populated state (2026-07-30 — EXPO boot TDZ)

*From the v9.49.28 boot crash: opening EXPO showed a blank board because a module-parse-time custom-recipe merge read `scheduleMode` (a `let` declared ~25,000 lines below it) in its temporal dead zone and threw, aborting the whole script. It only triggered when `pp_custom_recipes` held a recipe carrying `productionFacts`. This is a fresh instance of the 2026-06-20 "baseline blind spot" above, now on the **boot** path; the full record + staged fix is `conc-kitchen-expo/EXPO_BOOT_TDZ_FIX_AND_HARDENING_PLAN_2026-07-29.md`. Point at it before an EXPO boot-path change; don't restate.*

- **A long-lived single-operator app never does the one boot its whole test suite covers — the clean-install boot.** Every EXPO gate clears localStorage and boots empty, so the suite validated a boot that only a brand-new browser ever performs. The architect's real boot carries years of authored state (46 decisions, custom recipes, overrides), and the crash lived exactly there: the deployed app booted fine for everyone with an empty store — and for weeks in CI — while the returning user hit a blank board. "Green because the feature is inert at rest" (2026-06-20), applied to boot: **green because the store is empty at boot.** The durable guard is a **populated-state boot-smoke** — boot against a synthetic populated fixture and assert the primary artifact (the schedule) actually materializes. It catches a state-dependent boot failure regardless of *mechanism*, where a source-position gate only pins one declaration.

- **A boot-smoke's fixture must carry the state in the form that actually triggers the path — an inert-shaped seed proves nothing.** The crash only fires for a custom recipe whose facts *pass* the compiler and reach the site-resolution read; a recipe with no/invalid `productionFacts` early-returns before that line, so a fixture seeded with the inert form boots clean on the *broken* code and the gate is falsely green. Authored-to-fail is not "seed some state" — it is "seed the state that reproduces the failure, and prove red against the pre-fix build." (Here: proven locally — pre-fix 4-fail catching `Cannot access 'scheduleMode' before initialization`, post-fix 6-pass.) This is the hostile-state clause of the baseline blind spot, pointed at boot.

- **In a large single-file app, source declaration order is a load-bearing contract that nothing enforces.** Parse-time code (data-merge IIFEs, boot-time migrations) runs top-to-bottom during script evaluation; any such block that reads a `let`/`const` declared physically later is a latent TDZ crash that aborts the *entire* script — no error boundary, blank page. Two traps worth carrying: a `typeof x === 'function'` guard checks the *function* exists, not that the binding it reads is initialized (a false safeguard — it was the exact crash frame here); and `typeof` on a `let`/`const` in its TDZ **throws too**, so it can't guard the binding either. The fix is initialization order (declare shared runtime state above its earliest parse-time reader) — the derive/declare-order sibling of "single source, kept single."

## Shrink the ceremony, never the boundary — locate the real enforcement first (2026-08-11 — CODEX recipe-flow simplification)

*From the S0–S6 line that gave dish-rename, two shelves, one-tap Library adds, edit-never-demotes, seed-merge honesty, and the Release Queue — ending in a Jason-ruled removal of a publish blocker. Full record: `conc-recipe-hub/docs/CODEX_RECIPE_FLOW_SIMPLIFICATION_CLOSEOUT_2026-08-11.md`. Sharpens "match the ceremony to the stakes" (#2) with where the boundary actually lives.*

- **Ceremony accretes next to a safety boundary and gets mistaken for it — before you defend OR remove a friction, name where the enforcement actually lives.** CODEX's felt "safety" (four browse tabs, a submit step, curator gates, a promote ceremony, a feed-size publish blocker) was *not* what keeps a bad recipe off a plating sheet — **publish authority** (a non-seed record is `publishAuthorized:false` by construction), the per-record publish-dry-run blockers, the GitHub token, and the re-bless ritual are. Once the real net is *named*, the surrounding ceremony is free to cut: the whole line shrank the friction to one tap while the boundary never moved, each slice proving it (feed-byte-neutral + a gate that the authorization checks still fire). The failure of skipping this audit is bilateral — you either defend friction that protects nothing, or you delete a guard that *is* the net. **Proximity to the boundary is not membership in it.**

- **The kitchen unable to work is a bigger, likelier harm than a smoothable data imperfection — a guard earns its *block* only when being-wrong is catastrophic, not when it's tidy.** Jason's ruling, worth keeping verbatim: *"minimize friction… I can't see a scenario where a feed size change will be catastrophic… the biggest problem is the kitchen not being able to do what it needs to do — a schedule blocked by some arbitrary check we offhandedly decided was important due to perfectionism."* The operating discriminator on top of #2 — three tests to *pull* a guard: (a) it fires on normal, approved operations (cry-wolf), (b) a stronger, non-redundant net already covers the real risk, (c) the cost of it being wrong is something the kitchen absorbs, not a safety event. All three held for the record-count blocker; none held for the per-record authority checks — so one went and the others stayed. "Trust the kitchen to smooth jagged edges" is a design input, not a concession.

- **A check whose "expected" value is a hand-frozen snapshot rots into a false-alarm generator — and a guard that cries wolf spends the credibility of the guards that matter.** `CODEX_FEED_BASELINE` froze the feed sizes (224/131) on a capture date; the feeds legitimately grew to 240/240 and the check hard-blocked publishing for weeks with nothing wrong, because a frozen constant cannot tell *approved growth* from *an accident* — it fires on both and must be hand-reset forever. Same shape as HUB's freshness incident (two version numbers sitting in memory that nobody compared — see the HUB CLAUDE.md, 2026-07-27) and its deliberately-*generous* 14-day stale threshold (tight thresholds cry wolf weekly and get tuned out). **If a check's expected value is a snapshot someone must remember to update, it will drift — derive it from a live source of truth, demote it from blocker to warning, or delete it.**

- **Before treating the presence of a field as a provenance signal, verify which code paths actually write it — the obvious signal is often stamped by machinery you forgot about.** The seed-merge honesty fix needed "is this production record a pristine seed copy, or locally edited?" The obvious answer — *does it have `history`?* — was a booby-trap: the boot migration stamps a `created` history entry (and an empty `cookLog`) onto **every** record, so "has history" means nothing. The correct discriminator keys only on artifacts that *exclusively* the intended action writes (`contentFingerprint`, a `revision_approved` history action, a destination receipt, `publishAuthority`), confirmed empirically by grepping the writers. The adversarial-review **P1** this surfaced was food-safety: an *approved revision* — a real, common state the first draft's signal missed — would have been silently clobbered back to stale seed content on an unrelated release. **A provenance discriminator must enumerate every real state the field can hold and rest only on writes you have verified.** (Same line, intake corollary — "trusted local data expires" (§XSS) grown a build rule: at an import boundary *rebuild* the record from an explicit content whitelist rather than spreading the incoming object; untrusted input must never become a trusted record by inheritance. And pin a currently-inert defensive strip with a **source-scan**, not a runtime assertion that would pass vacuously whether the strip is present or not.)
