### E-2-7 · `completeSwap` bypasses the Decision Ledger entirely — a raw schedule mutation with a duplicated holdDays formula and no over-hold confirm (the one verb the Kernel migration missed)
- class: footgun
- severity: P1
- status: NEW
- confidence: verified (both functions read at HEAD; call graph confirmed reachable from a live edit-panel button)
- where: `index.html:23372-23433` (`startSwap`/`completeSwap`), reachable via `:26252` (`onclick="startSwap(...)"`, the edit panel's "⇄ Swap" verb card — sibling to Move/Pin/Remove/Reset per the v9.37 changelog); contrast `moveItemToDay` `:20461-20530` and `commitBoardMove` (outside slice, ~:33398) which both write Decisions.
- what: Every other board verb (suppress, move/relocate, SET, ADD) was migrated onto the Decision Ledger through the v9.33–v9.36 Kernel work — the generator "reads Decisions before it builds," so nothing races `runScheduler()`. `completeSwap` was never migrated: it directly splices the two items between `schedule[week][day]` arrays (`:23404-23413`), recomputes each item's `holdDays` with a **hand-rolled duplicate** of the modulo formula (`:23418/23422 — ((svcIdx - linearIdx(...)) % 28 + 28) % 28`) instead of calling the shared `deriveHoldDays()` that `moveItemToDay` (`:20498`) and three other in-range siblings (`:23827`, `:24220`, `:24400`) all use, and its only "audit trail" is the in-memory `_editLog` (`trackEdit` at `:23327-23330` — a display-only array feeding a UI badge, not `pp_ledger`). It re-renders (`renderStats/renderCalendar/renderBoard`) but never calls `runScheduler()`, so the mutation is visible immediately but is not a Decision the next Generate/Rebuild will replay. Additionally: `moveItemToDay`'s callers gate an over-hold move behind a styled hard-confirm (`.hold-stop-overlay`, per the Slice-2/K-P2d changelog — `hold > maxHoldDays` blocks with a confirm) — `completeSwap` has **no such check at all**, so a swap that pushes an item's cold-hold past its safety limit commits silently.
- evidence: `:23415-23423` (raw `%28` formula, no `deriveHoldDays` call) vs `:20498` (`const derivedHold = ... : deriveHoldDays(...)`); `:23425` (`trackEdit('swap', ...)` — display-only, confirmed via `trackEdit`'s body at `:23327-23330`, no `_ledger`/`makeDecision` reference); no `maxHoldDays`/`hold-stop-overlay` token anywhere in `startSwap`/`completeSwap`'s 62-line body.
- consequence: A supervisor using the Swap verb (offered as a first-class action right beside Move in the same edit-panel card row) reasonably expects Swap's permanence to match Move's. It doesn't: the swap is silently discarded on the next full Generate (the exact "my edit disappeared" class the entire Ledger/Kernel line — CLAUDE.md's Footguns #3, the v9.19/v9.20/v9.34 "make it stick" arc — was built to eliminate everywhere else), and in the interim it can leave an item held past its safe cold-chain window with zero warning where the twin Move gesture would have blocked or hard-confirmed.
- direction: Existing seam, directly available: route `completeSwap` through two `moveItemToDay`-style relocate Decisions (or a small `swap×global` Decision pair) using the already-shared `deriveHoldDays()` + the same over-hold hard-confirm gate `commitBoardMove` already applies, then `await runScheduler({skipBarrier:true, suppressAutoPublish:...})` to re-derive — mirroring the pattern Move/Pin/Remove/Reset already use in the same panel.
