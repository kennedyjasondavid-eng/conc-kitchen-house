### E-1-5 · The no-op-republish guard's own write can silently fail, regressing the exact duplicate-publish bug it was built to prevent
- class: footgun
- severity: P1
- status: NEW
- confidence: verified
- where: `conc-kitchen-expo/index.html:22701-22707` (the read-side skip guard) and `:22763` (the write-side, right after a successful push, inside a bare `try{}catch(e){}`)
- what: `publishHubSchedule({auto})`'s dedup guard compares `localStorage.getItem('pp_last_published_version')` against the current board's content hash and skips a no-op auto-publish on a match (`:22701-22707`) — this is precisely the fix EXPO shipped in v9.31.11 ("Guard boot auto-publish against no-op republishes") after duplicate boot-publish commits and `422 "Update is not a fast forward"` races were observed on the live HUB repo. A second write site at `:22721` (a legacy-hash-migration branch of the same guard) carries the identical silent-catch pattern.
- consequence: If this specific `setItem` throws (shared-origin quota pressure — plausible on a device also running DOOR/MISE/HUB per the shared-github.io-origin design; Safari private mode; or any other quota edge) the GitHub push itself has *already succeeded* (no board corruption), but the local guard silently fails to update. Routing this write through the same helper (or at minimum upgrading the bare `catch(e){}` to a `console.warn` so a failure leaves a trace) would make the failure mode visible instead of silent, consistent with lens #5 ("silent failure on a load-bearing write is the worst class").
