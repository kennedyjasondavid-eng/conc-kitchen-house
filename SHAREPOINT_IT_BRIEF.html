1Summary

CONC's kitchen runs on HOUSE — five in-house browser apps that plan, route, and report shelter catering across the Bloor and Rexdale kitchens. They were built deliberately on infrastructure the organization already owns: single HTML files, no servers, no vendors, no licence costs.

Today the apps are hosted on GitHub Pages and move their shared data through GitHub, under a personal account. We want to bring the data home to CONC's Microsoft 365 tenant in stages, with app hosting as the deliberate final step.

Most of the groundwork already exists inside the apps — two ship complete Microsoft sign-in + Graph API clients that are dormant only because no Entra app registration exists yet; a third was written with named "swap to SharePoint here" seams.

The near-term ask is two items of standard M365 administration:

① A governed SharePoint document library — folders, permission groups, retention labels, version history — so PROOF, DOOR, and EXPO can start putting files on the shared drive immediately, and ② one Entra app registration (single-page app, delegated Graph permissions, no client secret) so the apps can read and write those files as the signed-in user. Nothing in this plan asks IT to run, host, or maintain software.

3SharePoint already touches HOUSE

This is not a greenfield ask — the integration surface already exists:

~148 recipe links in HUB point at Excel recipe cards in conctoronto.sharepoint.com/sites/Kitchen/…/Bloor/Recipes/. Staff follow HUB → SharePoint every day.
DOOR carries SharePoint settings — a tenant base URL and a pilot output-folder deep link under the Kitchen site — plus staff-facing copy already promising "automatic archiving to SharePoint."
HUB & CODEX ship complete Graph clients — Microsoft sign-in (MSAL, single-page-app flow, no secrets), site-profile sync, recipe archive upload, a shared review queue. All dormant awaiting a Client ID.
A written provisioning request exists — CODEX's repo has carried an Entra app-registration request since June 20, 2026. Section 5-B here generalizes it to all the apps.
DOOR has named swap seams — three isolated persistence functions whose comments read "swap this for a SharePoint write via Microsoft Graph — call sites don't change."
PROOF's sensitive tier is fully specified — exact workbook schemas, permission groups, and retention labels are documented and waiting. Zero code needed; only the Stage-1 setup.

One inconsistency to resolve: two tenant hostnames appear in app configuration — conctoronto.sharepoint.com (hardcoded recipe links, DOOR's default) and conc.sharepoint.com (the configurable default in HUB and CODEX settings). Please confirm the canonical tenant and site so we can align the defaults.

5The staged plan

1

A governed SharePoint home no code — pure M365 administration

Create the document library structure, permission groups, retention labels, and version history (details right), and provision OneDrive sync on the named kitchen machines.

Outcome: PROOF goes live against real workbooks; DOOR/EXPO/PROOF file outputs land on the shared drive through the sync client — the file-drop capability with zero code changes.

2

One Entra app registration the single biggest unlock

A single-page-application registration with delegated Graph permissions. Apps act only as the signed-in user — no service accounts, no secrets, no standing credentials.

Outcome: HUB's site-profile sync and CODEX's recipe archive + review queue go live as already built; DOOR/EXPO gain in-app "save to SharePoint" at their prepared seams (kitchen-team code work, not IT's).

3

Runtime data moves home multi-device sync

Swap browser-local state to Graph-backed storage at the named seams, one function at a time, app by app. The GitHub JSON transport between apps can remain during this stage; candidates migrate as they prove out.

4

Identity everywhere

Staff sign in with CONC Microsoft accounts; pasted GitHub tokens and the portal PIN retire from day-to-day flows. All staff already hold M365 credentials, so this is configuration, not provisioning. Needs IT's input on conditional access and shared-device policy for kitchen tablets.

5

Hosting last, by design

Move the apps off the personal GitHub Pages account. They are static files, so the requirement is modest: HTTPS static hosting + the JSON feeds served alongside. Options to discuss: an org-owned GitHub organization, Azure Static Web Apps on CONC's tenant, or existing org infrastructure — your call, not ours to prescribe.

Sequencing rationale: Stages 1–2 capture most of the governance value — sensitive data under M365 controls, org-owned copies of operational outputs — at near-zero risk, while the apps keep running exactly as they do today. Hosting moves last because it's the most disruptive change and the least urgent: the public static pages expose no sensitive data.

6The concrete ask — Stages 1–2

A · SharePoint site & library (Stage 1)

  1. Confirm the canonical tenant + site — we believe conctoronto.sharepoint.com, site /sites/Kitchen.
  2. Create the folder structure: 
    Operations Reporting/
  PROOF Tier-2/
    Active/      ← LOG · CREW · LEDGER (live workbooks)
    Closeouts/   ← month-end frozen copies
    Outputs/     ← generated report PDFs
Kitchen Ops/
  DOOR Outputs/  ← compliance exports · change-log
  EXPO Outputs/  ← order sheets · schedule snapshots
    Workbook schemas, columns, and dropdowns are fully specified in conc-kitchen-proof/SHAREPOINT_SETUP_CHECKLIST.md.
  3. Permission groups per file/folder: PROOF-Log (managers only), PROOF-Crew & PROOF-Ledger (director / admin / bookkeeper + kitchen lead), plus a kitchen-ops group. No org-wide access; no anonymous links.
  4. Retention labels per CONC policy: finance (LEDGER), HR (CREW), incident/legal (LOG).
  5. Version history on for the library.
  6. OneDrive sync of PROOF Tier-2/Active and Kitchen Ops/ on the named kitchen machines (we'll supply the list).

B · Entra app registration (Stage 2)

  • Platform: single-page application.
  • Redirect URIs: the app origins — currently the five https://kennedyjasondavid-eng.github.io/conc-kitchen-*/ URLs; updated when hosting moves at Stage 5.
  • API permissions (delegated): Microsoft Graph User.Read, Files.ReadWrite.All; optionally Mail.Send (one CODEX email-notify helper — skippable).
  • Admin consent granted if CONC policy requires it.
  • No client secret, certificate, or service account — the apps are browser-only; MSAL handles sign-in in the user's session, and every action is bounded by what that user can already access in SharePoint.
  • Deliverable back to us: the Application (client) ID — and Tenant ID if tenant-restricted sign-in is required. Both are public identifiers, entered in each app's settings screen.

If CONC prefers tighter scoping than Files.ReadWrite.All, we're glad to work with Sites.Selected scoped to the Kitchen site instead — whichever fits your permission model.

7Decision points where we need IT's judgement

  1. Canonical tenant/site — conctoronto vs conc.
  2. Permission scoping — delegated Files.ReadWrite.All (simplest; user-bounded) vs Sites.Selected (tighter; slightly more setup).
  3. Retention label names — what CONC policy calls the finance / HR / incident-legal labels.
  4. Shared kitchen tablets — the HUB board is anonymous-read today by design. When runtime data moves (Stage 3+): keep the aggregate schedule feed public, or adopt a shared-device / kiosk sign-in pattern? What's CONC's stance on shared-device Entra sign-in?
  5. Hosting target (Stage 5, no urgency) — org GitHub organization vs Azure Static Web Apps vs existing org infrastructure.

8What we are not asking for

  • No servers, databases, or VMs to run or maintain
  • No new accounts or licences — all staff already have M365 credentials
  • No software purchases or vendor onboarding
  • No custom development from IT — the kitchen team writes and maintains the apps
  • No service accounts, stored secrets, or standing credentials
  • No migration of resident-identifying data — it stays on-device in DOOR unless a future stage is separately reviewed

The division of labour we're proposing: IT owns tenancy, identity, and governance; the kitchen team owns the apps. Stages 1–2 are a few hours of standard M365 administration that unlock work the apps are already built for.
