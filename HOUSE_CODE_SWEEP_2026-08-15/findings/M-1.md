## Findings

### M-1-1 · Anthropic API "Smart Mode" translator is completely non-functional in every real browser (missing CORS opt-in header)
- class: kludge
- severity: P1
- status: NEW
- confidence: verified (empirically reproduced against the live `api.anthropic.com` endpoint, not from training-data recall)
- where: `index.html:16671-16733` (`translateSmart`), `:22761` (`testApiKey`, boundary of M-2's range but same defect), wired from `:4627-4628` and `:15598-15617`
- what: Both fetch calls to `https://api.anthropic.com/v1/messages` send only `Content-Type`, `x-api-key`, and `anthropic-version` — none include the `anthropic-dangerous-direct-browser-access: true` header the Anthropic API requires to allow a CORS preflight from a browser origin. Every user who pastes an API key, enables "Smart Mode" in Settings → AI, and pastes a recipe hits this: `translateSmart` always throws (caught by its own `try/catch`, silently falls back to `translateDumb` with the copy "Smart parse failed (...) — falling back to standard parser"), and the separate `testApiKey()` "Test" button always reports "✗ Request failed" — even for a perfectly valid key.
- evidence: Live curl against the real endpoint reproduces the app's exact header set and origin: `curl -X OPTIONS https://api.anthropic.com/v1/messages -H "Origin: https://kennedyjasondavid-eng.github.io" -H "Access-Control-Request-Headers: content-type,x-api-key,anthropic-version"` → **`HTTP/2 400`**, body `Disallowed CORS origin`, no `access-control-allow-origin` header at all. Re-running the identical request with `anthropic-dangerous-direct-browser-access` added to the requested header list → **`HTTP/2 200`**, `access-control-allow-origin: *`. The app's code (`index.html:16716`: `headers:{'Content-Type':'application/json','x-api-key':apiKey,'anthropic-version':'2023-06-01'}`; `:22761` identical set) never sends that header, so a real browser's automatic preflight will always match my first (rejected) request, not my second (accepted) one.
- consequence: The "AI Features" tab (Settings), its "Test" button, "Smart Mode" toggle, and the "$0.001–$0.003 per translation" cost note are all dead UI — the feature has never worked in a deployed browser session (this is not new-since-June breakage; the two call sites are structurally identical and have carried this gap since the feature was introduced, so it predates the June XSS pass and every session since). No food-safety or data-loss impact (it fails closed into the existing "dumb" parser), but it is a trust-surface defect: a correct API key reports "Request failed", which reads to an operator as "my key is bad" rather than "this app can't call this API from a browser," and could cost real troubleshooting time or make someone conclude the whole AI feature is broken/abandon a valid key.
- direction: Add `'anthropic-dangerous-direct-browser-access': 'true'` to the headers object at both call sites (`:16716` and `:22761`). This is the documented, supported way to allow a purely client-side single-file app (this repo's whole architecture) to call the Anthropic Messages API directly from a browser — no server/proxy needed, consistent with the "no build step, no server" constitution. (Flagging, not fixing — analysis-only per sweep rules.)

### M-1-2 · `saveCostOverrides` silently swallows a write failure; its newer sibling `saveCostPriceLedger` (same subsystem, ~1000 lines later) does it right
- class: kludge
- severity: P2
- status: NEW
- confidence: verified
- where: `index.html:5456-5459` (`saveCostOverrides`) vs `:6431-6440` (`saveCostPriceLedger`); call sites at `:21774/21782/21820/21833` confirm the legacy path is still live, not dead code
- what: `saveCostOverrides(data)` does `try { localStorage.setItem(COST_OVERRIDES_KEY, JSON.stringify(data)); } catch(e) {}` — on quota-exceeded or a blocked write, the caller gets no signal at all; `_costOverridesCache` is already updated in memory (line above the try), so the UI keeps behaving as if the save succeeded until the next reload silently reverts it. Confirmed still called from 4 live sites in the Cost Editor UI (`renderCostEditorTable`/`renderCostAdditionsList` handlers, out of my range but the call sites prove liveness) — this is not a retired store despite the newer cost-price-ledger system existing alongside it. Contrast: `saveCostPriceLedger` in the same cost subsystem, added later, does the identical `localStorage.setItem` under `try`, but on catch returns `{ ok:false, errors:['LEDGER_STORAGE_FAILED'], warnings }` — an honest, structured, checkable failure.
- evidence: `function saveCostOverrides(data) { _costOverridesCache = data; try { localStorage.setItem(COST_OVERRIDES_KEY, JSON.stringify(data)); } catch(e) {} }` vs `function saveCostPriceLedger(input) { ... try { localStorage.setItem(...); return { ok: true, ... }; } catch (error) { return { ok: false, errors: ['LEDGER_STORAGE_FAILED'], warnings }; } }`
- consequence: A curator editing a cost override (price/supplier correction) in the Cost Editor whose browser is near its localStorage quota (plausible on the same shared github.io origin the KNOWN.md register already flags for storage-budget concerns in EXPO) can have the edit accepted in-UI and then silently lost on next load, with zero indication anything went wrong. Not food-safety; it is real data loss on a curator-facing editing surface, and it's the textbook "silent failure on a load-bearing write" lens with the fix already demonstrated in the same file.
- direction: Mirror `saveCostPriceLedger`'s pattern — return `{ok:false}` on catch and have the (out-of-range, M-2-owned) UI callers surface it, the same way the newer ledger path already does. No new mechanism needed; the sibling function is the existing in-house seam.
