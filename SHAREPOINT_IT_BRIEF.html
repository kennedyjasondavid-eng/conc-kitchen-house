1Summary

CONC's kitchen runs on HOUSE — six browser apps that plan, route and report shelter catering across the Bloor and Rexdale kitchens. They were built on infrastructure the organization already owns: single HTML files, no servers, no vendors, no licence costs.

Today the apps are hosted on GitHub Pages under a personal account, and move their data through GitHub. We want to bring that home to CONC's Microsoft 365 tenant in stages.

Most of the groundwork exists already. Two apps ship complete Microsoft sign-in and Graph clients, dormant only because no app registration exists; a third was written with named "swap to SharePoint here" seams. The near-term ask needs only standard M365 administration:

  1. A governed SharePoint document library — folders, permission groups, retention labels, version history — so PROOF, DOOR and EXPO can put files on the shared drive immediately.
  2. One Microsoft Entra app registration — single-page application, delegated permissions, no client secret — so the apps can read and write those files as the signed-in user.

Nothing here asks IT to run, host or maintain software. IT owns tenancy, identity and governance; the kitchen team owns the apps.

The data-classification story, in 60 seconds. Resident data never leaves the DOOR browser. What DOOR publishes outward are counts and totals, with no names attached. Everything currently on GitHub is operational, non-personal data — menus, recipes, cook times, schedules. The genuinely sensitive material (incidents, certifications, spend) does not exist yet, because it was always intended to live in SharePoint under CONC's governance. That is the largest single reason for this request.

3SharePoint already touches HOUSE

This is not a greenfield ask. The integration surface is already in place and in daily use:

143 recipe links in HUB point at Excel recipe cards on the Kitchen site. Staff follow HUB → SharePoint every day, today.
DOOR carries SharePoint settings — a tenant base URL and a pilot output-folder deep link — plus staff-facing copy already promising "automatic archiving to SharePoint."
HUB & CODEX ship complete Graph clients — Microsoft sign-in (MSAL, single-page-app flow, no secrets), site-profile sync, recipe archive upload, a shared review queue. All dormant awaiting a Client ID.
A written provisioning request has been open since June 20, 2026 — over four months. It stalled because there was no clear owner and no obvious place to start, which this brief is meant to fix.
DOOR has named swap seams — three isolated persistence functions whose comments read "swap this for a SharePoint write via Microsoft Graph — call sites don't change."
PROOF's sensitive tier is fully specified — exact workbook schemas, permission groups and retention labels documented and waiting. Zero code needed; only the Stage-1 setup.

One inconsistency for IT to resolve. Two tenant hostnames appear across the apps, and they disagree — HUB carries 430 references to conctoronto.sharepoint.com and DOOR 10, while CODEX uses conc.sharepoint.com in all 56 of its references. This is not a stray default: two apps assume one address and a third assumes the other. Whichever is canonical, the other needs a sweep. This is the cheapest question here and it blocks the rest.

5The staged plan

0

CONC takes ownership of the code kitchen-team work — new, and now first

Create a GitHub organization owned by CONC and transfer all six repositories into it. An organization rather than an account in CONC's name: several owners, a membership roster, an audit log, and the code belongs to the organization rather than a person. Transfer rather than copy, so history, issues and the reasoning behind every change survive, and the old addresses redirect.

The work is in the addresses, not the move — 132 web addresses are written into the code across the six repositories and must change together. It is a planned cutover, done out of service hours, because HUB is the board staff read during service.

Outcome: nothing load-bearing sits on a personal account, and the redirect address Microsoft is told to trust is one CONC controls. From IT we need only a decision on the owner address — ideally a role mailbox, with two owners.

1

A governed SharePoint home no code — pure M365 administration

Create the document library structure, permission groups, retention labels and version history (details in §6), and provision OneDrive sync on the named kitchen machines.

Outcome: PROOF goes live against real workbooks; DOOR/EXPO/PROOF file outputs land on the shared drive through the sync client — with zero code changes. Nothing in this stage waits on anything else in this brief.

2

One Entra app registration the single biggest unlock

A single-page-application registration with delegated Graph permissions. Apps act only as the signed-in user — no service accounts, no secrets, no standing credentials.

Outcome: HUB's site-profile sync and CODEX's recipe archive + review queue go live as already built; DOOR/EXPO gain in-app "save to SharePoint" at their prepared seams (kitchen-team code work, not IT's).

3

Runtime data moves home multi-device sync

Swap browser-local state to Graph-backed storage at the named seams, one function at a time. The existing transport keeps working throughout, so there is no flag day.

Outcome: the schedule stops living on a particular computer. Any supervisor, on any machine, sees the same current state.

4

Identity everywhere retires the current credential arrangement

Staff sign in with CONC Microsoft accounts. Today's arrangement — GitHub tokens pasted into a browser in plain text, long-lived, invisible to CONC and unrevocable by IT, plus a shared portal PIN — goes away. All staff already hold M365 credentials, so this is configuration, not provisioning.

Outcome: short-lived tokens issued by Microsoft, central revocation, MFA available, sign-in activity visible. IT input needed on conditional access and shared-device policy.

5

Hosting, finished largely resolved by Stage 0

With the repositories in a CONC organization, what remains is a choice of where the static files are served from — the org's own GitHub Pages (smallest change) or Azure Static Web Apps on CONC's tenant (Entra auth built in, nonprofit credits apply). SharePoint page hosting is likely a poor fit for full JavaScript apps, but that is IT's call.

  4. Retention labels per CONC policy — finance (LEDGER), HR (CREW), incident/legal (LOG).
  5. Version history on for the library.
  6. OneDrive sync of PROOF Tier-2/Active and Kitchen Ops/ on the named kitchen machines (list supplied).

The three workbooks are prepared as templates with correct columns and dropdowns — they need uploading, not authoring. Full spec in SHAREPOINT_SETUP_CHECKLIST.md.

B · Entra app registration (Stage 2)

  • Platform: single-page application. Not "Web" — that expects a server-side secret these apps do not and must not have.
  • Account types: single tenant — this directory only.
  • Redirect URIs: one per app, supplied by us once Stage 0 settles the addresses.
  • API permissions (delegated): User.Read + Sites.Selected scoped to the Kitchen site. Mail.Send, mentioned in July, has been dropped.
  • Implicit grant: both boxes unticked.
  • No client secret, no certificate, no service account. Sign-in and tokens are handled by Microsoft's own library in the user's session.
  • Admin consent granted if CONC policy requires it.

Deliverable back to us: the Application (client) ID, and the Directory (tenant) ID if tenant-restricted sign-in is required. Both are public identifiers, entered in each app's settings screen.

7Why these settings

We went looking for the weak points in our own proposal before asking IT to approve it.

Start from the baseline. Signing in with Microsoft is a substantial improvement on what HOUSE does today. Access is currently a GitHub token pasted into a browser in plain text — long-lived, invisible to CONC, unrevocable by IT. Replacing that with Microsoft sign-in means short-lived tokens, central revocation, MFA, and an audit trail. The code already discards tokens when the tab closes and holds no secret of any kind. The question is not whether sign-in introduces risk — it removes a good deal. It is whether we introduce any new exposure while doing it. Two things would.

How much the apps can reach. Files.ReadWrite.All sounds like "the kitchen's files." It means every file the signed-in person can reach anywhere in the tenant — so the reach is set by the most senior person who ever signs in. Sites.Selected confines the apps to the Kitchen site. We are asking for the narrower one. In fairness: it needs an extra administrative step, and our code currently requests the broad one, so choosing it means a small change on our side. We are volunteering that work, not pretending it is free.

Who controls the sign-in address. After sign-in, Microsoft returns the user to an address listed in the registration. Today that address sits on a personal GitHub account.

Together these are the finding. Separately each is tolerable. As things stand, a compromise of that account means a wrong dinner schedule on a tablet. Combine a broad permission with an address CONC does not control, and the same compromise means attacker-supplied code at a trusted sign-in address, using real staff sessions against tenant files. That is why Stage 0 moved to the front: the July brief had hosting last, reasoning that public static pages expose nothing sensitive — true then, and untrue the moment staff sign in.

If Sites.Selected proves awkward in CONC's tenant, Files.ReadWrite.All after Stage 0 is a defensible interim. The dangerous combination is the broad permission together with the uncontrolled address, not the permission alone.

Two smaller disclosures. The apps are hand-written HTML with no framework, so we do our own escaping of text that staff and the menu system put on screen; confining the permission is what limits the consequence, and is the second reason we ask for Sites.Selected. And the Microsoft sign-in library is a few versions behind (2.38.3, from Microsoft's own CDN) — no known exposure for our use, but we will bring it current as part of this work.

8Decisions we need from IT

  1. Canonical tenant/site — conctoronto vs conc (§3).
  2. Who creates the library, and by when — a name and a date. Needs nothing from us.
  3. Permission scoping — Sites.Selected (preferred) vs Files.ReadWrite.All; is the narrower one workable in this tenant?
  4. GitHub organization owner address — ideally a CONC role mailbox, with two owners.
  5. Retention label names — what CONC policy calls the finance / HR / incident-legal labels.
  6. Shared kitchen tablets — our recommendation is the staff board stays sign-in-free, so no unattended device holds a session. Needed before Stage 3.

One item is genuinely time-sensitive. LOG.xlsx is an incident log, and an incident log is forward-only — incidents and near-misses from before the file exists cannot honestly be reconstructed. Roughly four months of that history has already gone unrecorded, and the kitchen's HACCP plan assumes an incident record exists. We cannot recover it; we can stop losing more. If only one thing comes out of this, we would like it to be Stage 1, with a name and a date against it.

9What we are not asking for

  • No servers, databases or VMs to stand up or maintain.
  • No new accounts or licences — every staff member already has Microsoft 365.
  • No software purchases, no vendor onboarding.
  • No custom development from IT — the kitchen team writes and maintains the apps.
  • No service accounts, stored secrets or standing credentials held by the apps.
  • No ongoing administrative burden — Stages 1 and 2 are set up once.
  • No migration of resident-identifying data. It stays in DOOR, on-device, unless a future stage is separately reviewed.

IT owns tenancy, identity and governance. The kitchen team owns the apps. We are not asking to blur that line — we are asking you to exercise your half of it so we can finish ours.
