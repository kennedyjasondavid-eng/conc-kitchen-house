- consequence: if two CODEX recipe names share a 12-character prefix collision (or one contains the other's first-12-chars) — plausible among 224+ recipe names with shared dish-family prefixes (e.g. "Roasted Vegetable Sandwich" / "Roasted Vegetable Medley" both reduce to "Roasted Vege…") — the schedule item's "recipe" deep-link silently opens whichever name the fetch/cache happened to iterate first, not necessarily the correct one. A cook clicking through for instructions/quantities lands on a different dish's recipe with no indication anything was inexact. This is exactly the risk class the sibling function's own comment names ("a wrong X is worse than none") — just not applied here.
- direction: Reuse the sibling's own pattern in the same function neighborhood: collect all fuzzy hits into a `Set`, return the URL only when exactly one name matches, else fall through to the SharePoint `rcpUrl()` fallback (which is itself longest-match-first and safer). No new mechanism needed — the fix is 5 lines mirroring code already sitting 17 lines above it.
